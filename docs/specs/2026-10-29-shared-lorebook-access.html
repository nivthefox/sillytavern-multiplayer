Shared Lorebook Access

October 29, 2026

Working draft · Ready for review

Problem

The owner’s lorebooks are isolated in their account, so a guest’s SillyTavern frontend and its extensions cannot read them while participating in the shared chat.

Solution

This work implements the addon entirely in the frontend/browser. It makes no server-side or Plugin changes.

Participants’ frontends fetch the shared chat’s available lorebooks from each book’s source account over HTTP. The addon integrates these shared books with SillyTavern’s normal lorebook access mechanisms for read-only frontend and extension use.

Behavior

Every browser other than the selected owner follows the guest behavior in this specification, including additional owning-account tabs.

Available lorebooks

The shared chat’s available lorebooks are the union of the owner’s selections in “Active World(s) for all chats,” the chat-linked book, the owner’s active-persona book, and both the primary and additional lorebooks linked to every character in the group, including disabled members. Character-linked availability does not change with the character selected to generate a response. Sharing covers each book’s complete contents, including disabled entries and GM secrets, regardless of which entries activate for an AI response.

Each guest’s active-persona lorebook is also shared with the owner and the other participants, with the guest’s account remaining its source. The owner’s frontend includes its entries in normal lorebook evaluation during AI generation, subject to native activation rules and token budgets. Shared books are distinguished by source account as well as book identity, so identical names in different accounts do not resolve to the same book.

The advertised list updates immediately when the owner or guests change relevant selections.

Owner lorebook contribution

The selected owner browser publishes the owner-side union defined under Available lorebooks through multiplayer.lorebooks.set, following the Server Plugin’s Lorebook list events contract. Its contribution uses the books’ native filenames.

It republishes whenever a relevant selection changes. Each publication rebuilds the union from the current associations, so removing one association retains a book still included by another.

Guest lorebook contribution

Each guest browser publishes its persona-book contribution through multiplayer.lorebooks.set, following the Server Plugin’s Lorebook list events contract. It supplies the active persona’s linked book filename, or an empty contribution when no book is linked.

When the active persona’s book selection changes, including through switching personas, changing the linked book, or clearing the link, the addon publishes the guest’s current contribution.

Joining and reconnecting

The addon uses the Server Plugin’s browser-library lifecycle and reconnection contracts. After each successful join or rejoin, it publishes its current contribution once local selections are loaded, following Owner lorebook contribution or Guest lorebook contribution. When bus.status assigns ownership to this browser, it publishes the owner’s contribution once local selections are loaded.

On bus.disconnected, the frontend retains its cached shared books. Other viewers also retain books already cached from a disconnected participant.

After rejoining, the addon refreshes the books in the current combined availability over HTTP, including cached books, to obtain changes saved while it was disconnected. Failed refreshes follow the existing load-error behavior under Edge Cases.

Receiving shared lists

The addon applies the lorebook list returned by each successful join and each multiplayer.lorebooks.changed update, following the Server Plugin’s Lorebook list events contract. Each supplied list replaces the previous Plugin-supplied list. Malformed updates leave that list unchanged.

Shared availability is the union of the Plugin-supplied list and the books found through Primary and chat-linked discovery below, deduplicated by source account and filename.

The addon fetches newly needed cross-account books through the Server Plugin’s Lorebook route, using each book’s source account and filename and the existing load-error behavior under Edge Cases. It retains cached contents for books still in the combined availability. After a list update, it stops exposing books omitted from both sources.

Primary and chat-linked discovery

The addon reads these links from the resources already loaded when opening the shared chat under Chat Ownership:

  • Primary character books: read data.extensions.world from each group member’s character card, returned by GET /accounts/<accountID>/characters/<characterID>/card.
  • Chat-linked book: read chat_metadata.world_info from the saved transcript’s metadata header, returned by GET /chats/<accountID>/groups/<groupID>/chats/<chatID>.

For each linked book, append .json to its native book name and fetch its contents through GET /accounts/<accountID>/lore/<filename>. The account identifier in these requests is the group’s owning account. Requests follow the Server Plugin’s Character card, Chat transcript, and Lorebook route contracts.

Guest frontend access

While the shared chat is open, SillyTavern and its extensions can resolve and read advertised books from other accounts as though they were local books. These books do not appear in the guest’s lorebook selector or editor, and shared access is read-only. Books in the guest’s own account keep their normal selector and editor access. Leaving the shared chat removes the cross-account availability provided by this feature.

Saved-book event

Event nameOriginDestination
multiplayer.lorebook.savedSaving browser’s addonall
Payload
FieldValue
filenameA string identifying the native lorebook filename including .json.

The saving browser’s addon publishes this event after a native save of a shared lorebook succeeds.

Save confirmation must establish that persistence succeeded. SillyTavern’s native lorebook-update event can fire after an unsuccessful HTTP response, and a debounced save helper can return before persistence. Neither is sufficient proof of a successful save. A failed save or an uncertain outcome, including a lost save response, produces no saved-book event.

The saving browser ignores its own event. Other viewing frontends identify the book using the bus-supplied sender.accountId and the body’s filename. Malformed notifications and notifications for books not currently shared in the open chat are ignored.

For a currently shared book, the receiving frontend fetches its saved contents through GET /accounts/<accountID>/lore/<filename>, using that source account and filename and following the Server Plugin’s Lorebook route contract. A successful read replaces the cached contents. Failed reads follow “A shared lorebook fails to load or refresh” under Edge Cases.

Deleted-book event

Event nameOriginDestination
multiplayer.lorebook.deletedDeleting browser’s addonall
Payload
FieldValue
filenameA string identifying the native lorebook filename including .json.

The deleting browser’s addon publishes this event after receiving a successful response to the native deletion of a shared lorebook. A failed deletion or an uncertain outcome, including a lost deletion response, produces no deleted-book event.

The deleting browser applies deletion cleanup locally and ignores its own event. Other viewing frontends identify the book using the bus-supplied sender.accountId and the body’s filename. For a currently shared book, they remove it from the locally held Plugin-supplied list, primary/chat-linked discovery, and cached contents. Malformed notifications and notifications for books not currently shared in the open chat are ignored.

Each frontend in the source account also withdraws the deleted filename from its contribution and republishes the remaining contribution through multiplayer.lorebooks.set. It does this after a local confirmed deletion or a deletion notification for its own account.

Edge Cases

A fetch finishes after the chat or shared availability changes
Discard the result if it belongs to a previously open chat or the book is no longer shared, so it cannot restore that book’s availability.
A shared lorebook fails to load or refresh
Show a load error and retain any previously cached contents. If no cached contents exist, leave the book unavailable. Do not treat a failed load as an empty book.
Shared books from different accounts have the same name
Both books remain accessible by their source-account-qualified identities. A name-only lookup reports ambiguity rather than selecting either book.
A shared book and a guest’s local book have the same name
Within the shared chat, name-based access resolves to the shared book without modifying the guest’s local book. Leaving the shared chat restores normal local resolution.

Testing Criteria

Tests run within the addon repository using fake Plugin responses, lorebook fixtures, and substitutes for SillyTavern’s interface, lorebook access, and generation. They require neither a live Plugin, a multi-account server, nor an AI service.

Lorebook contributions and selection changes

  • Given a selected owner with loaded global, chat, persona, and character lorebook selections, the addon publishes their native filenames as the owner’s contribution through multiplayer.lorebooks.set.
  • Given a browser receiving ownership through a join result or bus.status, it publishes the owner’s contribution after loading its local selections.
  • Given an additional owning-account tab, it publishes its persona-book contribution and follows the same guest behavior as every other non-owner browser.
  • Given group characters with primary and additional books, including a disabled member, all those books are advertised regardless of the character selected for generation.
  • Given a guest with an active-persona lorebook, the addon supplies that book’s native filename as the guest’s contribution through multiplayer.lorebooks.set.
  • Given a guest without a persona lorebook selected, the addon supplies an empty contribution through multiplayer.lorebooks.set.
  • Given a guest switching personas, changing the active persona’s linked book, or clearing the link, the addon publishes the current persona-book contribution.
  • Given a guest’s successful join with its local selections loaded, the addon publishes its current persona-book contribution, including an empty contribution when no book is selected.
  • Given a selected owner or guest successfully rejoining, it republishes its current contribution once local selections are loaded.
  • Given a successful join before local selections are loaded, contribution publication waits until those selections are available.
  • Given a shared book containing disabled entries and entries that did not activate in the latest response, reads return those entries along with the rest of the book.
  • Given a fetched guest persona book during owner-side generation, its entries enter native lorebook evaluation and remain subject to activation rules and token budgets.
  • Given an owner or guest changing a relevant selection, the addon republishes that browser’s current contribution without requiring the chat to be reopened.
  • Given an owner removing one association while another still includes the same book, the published contribution retains that book.

Shared lists and linked-book discovery

  • Given multiplayer.lorebooks.changed adding a previously unavailable cross-account book, the frontend fetches the newly needed book through the Plugin Lorebook route using the supplied source account and filename.
  • Given a shared-list update retaining a cached book, the frontend retains that book’s cached contents.
  • Given a shared-list update omitting a book still included by primary or chat-linked discovery, the frontend retains its shared availability.
  • Given a shared-list update omitting a previously advertised book that is also absent from primary and chat-linked discovery, the frontend stops exposing that book through shared reads.
  • Given a malformed shared-list update, the frontend leaves its current advertised list unchanged.
  • Given a successful chat join, the addon combines the supplied lorebook list with primary character books from the loaded cards and the chat-linked book from the loaded transcript’s metadata header.
  • Given the same source account and filename in both the supplied list and primary or chat-linked discovery, the combined availability contains that book once.
  • Given a discovered primary character or chat-linked book, the addon appends .json to its native book name and fetches its contents through the owner-qualified Plugin Lorebook route.

Frontend access

  • Given a shared chat advertising a book, a frontend or extension read obtains that book through HTTP using its advertised identity rather than resolving it to an unrelated local book.
  • Given an open shared chat, advertised books from other accounts are accessible through normal lorebook reads but absent from the guest’s lorebook selector and editor.
  • Given a guest whose own persona book is advertised, that book retains its normal local selector and editor access.
  • Given shared lorebook access, the addon exposes reads without introducing a shared-book save or change-request mechanism.
  • Given a user leaving a shared chat, that chat’s shared books are no longer available through the frontend’s shared access.

Disconnection and reconnection

  • Given an owner or guest disconnecting, other viewing frontends retain their already cached lorebooks.
  • Given bus.disconnected in a frontend with cached shared books, those books remain available in that frontend.
  • Given a successful rejoin with a cached book still in the combined availability, the frontend requests its saved contents over HTTP and replaces the cached contents after a successful read.

Saved-book notifications and refreshes

  • Given a confirmed successful native save of a shared lorebook, the saving browser sends multiplayer.lorebook.saved to all with a JSON object containing its native filename, including .json.
  • Given a native lorebook-update event or a completed save helper without confirmation that persistence succeeded, the addon sends no saved-book event.
  • Given a failed save or a lost save response, the addon sends no saved-book event.
  • Given the saving browser receiving its own multiplayer.lorebook.saved event, it does not fetch the book again.
  • Given multiplayer.lorebook.saved for a currently shared book and a successful HTTP read, another viewing frontend fetches the book through the Plugin Lorebook route using sender.accountId and filename and replaces its cached contents with the response.
  • Given a malformed saved-book notification or one identifying a book not currently shared in the open chat, the frontend ignores it without fetching a book or changing shared availability.
  • Given a fetch completing after the user switches chats, its result is discarded without restoring the previous chat’s shared books.
  • Given a fetch completing after its book is removed from shared availability, its result is discarded without restoring the book.

Deleted-book notifications and cleanup

  • Given a successful native deletion response for a shared lorebook, the deleting browser sends multiplayer.lorebook.deleted to all with a JSON object containing its native filename, including .json.
  • Given a failed deletion or a lost deletion response, the addon sends no deleted-book event.
  • Given the deleting browser receiving its own multiplayer.lorebook.deleted event, it ignores the notification.
  • Given multiplayer.lorebook.deleted for a currently shared book, another viewing frontend removes the book identified by sender.accountId and filename from its locally held Plugin-supplied list, primary/chat-linked discovery, and cached contents.
  • Given a local confirmed deletion of a shared book, the frontend republishes its remaining contribution through multiplayer.lorebooks.set without the deleted filename.
  • Given a frontend receiving a deletion notification for a currently shared book in its own account, it republishes its remaining contribution without the deleted filename.
  • Given a malformed deleted-book notification or one identifying a book not currently shared in the open chat, the frontend ignores it without changing shared availability or cached contents.

Load errors and name resolution

  • Given a failed shared-book refresh with an existing cached version, the frontend reports a load error and retains that version.
  • Given a failed shared-book read without cached contents, the frontend reports a load error and leaves the book unavailable rather than returning an empty book.
  • Given different source accounts advertising books with the same name, qualified reads return the corresponding books and a name-only lookup reports ambiguity.
  • Given one shared book with the same name as a guest’s local book, name-only access within the shared chat resolves to the shared book without modifying the local book, and leaving restores local resolution.
