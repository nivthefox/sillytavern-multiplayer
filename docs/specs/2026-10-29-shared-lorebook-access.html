Shared Lorebook Access

October 29, 2026

Working draft · Ready for review

Problem

The owner’s lorebooks are isolated in their account, so a guest’s SillyTavern frontend and its extensions cannot read them while participating in the shared chat.

Solution

This work implements the addon entirely in the frontend/browser. It makes no server-side or Plugin changes.

The owner’s shared chat advertises its available lorebooks, and the guest’s SillyTavern frontend fetches them from the owner’s storage over HTTP. The addon integrates these shared books with SillyTavern’s normal lorebook access mechanisms for read-only frontend and extension use.

Behavior

Available lorebooks

The shared chat’s available lorebooks are the union of the owner’s selections in “Active World(s) for all chats,” the chat-linked book, the owner’s active-persona book, and both the primary and additional lorebooks linked to every character in the group, including disabled members. Character-linked availability does not change with the character selected to generate a response. Sharing covers each book’s complete contents, including disabled entries and GM secrets, regardless of which entries activate for an AI response.

Each guest’s active-persona lorebook is also shared with the owner and the other participants, with the guest’s account remaining its source. The owner’s frontend includes its entries in normal lorebook evaluation during AI generation, subject to native activation rules and token budgets. Shared books are distinguished by source account as well as book identity, so identical names in different accounts do not resolve to the same book.

The advertised list updates immediately when the owner or guests change relevant selections. Each change replaces the affected association; a book remains available if another association still includes it.

Opening a chat while the owner is offline

A guest opening the shared chat without a connected owner can access its character-linked lorebooks and chat-linked lorebook. Persona and global lorebooks are not made available on that offline opening.

Guest frontend access

While the shared chat is open, SillyTavern and its extensions can resolve and read the advertised books as though they were local books, but the books do not appear in the guest’s lorebook selector or editor. Shared access provides a read mechanism only. Leaving the shared chat removes their availability from the guest’s frontend.

If a user disconnects, other users retain the already cached lorebooks.

Refreshing shared books

When a shared lorebook is successfully saved in its source account, viewing frontends refresh their cached contents from the saved book.

Edge Cases

A fetch finishes after the user switches chats
Discard the result so it cannot restore the previous chat’s shared lorebooks.
A shared lorebook is deleted from its source account
Remove the book from shared availability and clear its cached contents. Treat confirmed deletion separately from a load failure.
A shared lorebook fails to load or refresh
Show a load error and retain any previously cached contents. If no cached contents exist, leave the book unavailable. Do not treat a failed load as an empty book.
Shared books from different accounts have the same name
Both books remain accessible by their source-account-qualified identities. A name-only lookup reports ambiguity rather than selecting either book.
A shared book and a guest’s local book have the same name
Within the shared chat, name-based access resolves to the shared book without modifying the guest’s local book. Leaving the shared chat restores normal local resolution.

Dependencies

The Plugin specification must provide the following capabilities.

  • Lorebook discovery: supply participating accounts with the shared chat’s advertised lorebook list according to Available lorebooks in Behavior, retaining the source account in each book’s identity.
  • Shared-resource reads: provide authorized read-only cross-account HTTP access to fetch advertised books from their source accounts, including guest persona books.
  • Offline discovery: make character-linked and chat-linked books discoverable and readable without a connected owner browser.
  • Selection updates: distribute advertised-list changes to viewing frontends when participants change relevant selections.
  • Saved-book notifications: notify viewing frontends after a shared lorebook is successfully saved so they can refresh its contents.
  • Deleted-book notifications: notify viewing frontends when a shared lorebook is deleted from its source account, distinguishing confirmed deletion from a failed read.

Testing Criteria

Tests run within the addon repository using fake Plugin responses, lorebook fixtures, and substitutes for SillyTavern’s interface, lorebook access, and generation. They require neither a live Plugin, a multi-account server, nor an AI service.

  • Given an owner with global, chat, persona, and character lorebook selections, the advertised list includes each selected book with its source account and book identity.
  • Given group characters with primary and additional books, including a disabled member, all those books are advertised regardless of the character selected for generation.
  • Given a guest with an active-persona lorebook, that book is advertised to the owner and other participants with the guest’s account as its source.
  • Given a participant without a persona lorebook selected, no persona-book association is advertised for that participant.
  • Given a shared book containing disabled entries and entries that did not activate in the latest response, reads return those entries along with the rest of the book.
  • Given a fetched guest persona book during owner-side generation, its entries enter native lorebook evaluation and remain subject to activation rules and token budgets.
  • Given an owner or guest changing a relevant selection, the addon advertises the changed association without requiring the chat to be reopened.
  • Given a supplied advertised-list update, viewing frontends replace the affected association and retain a book still included by another association.
  • Given a guest opening a chat without a connected owner, character-linked primary and additional books and the chat-linked book are available, while persona and global books are not advertised.
  • Given a shared chat advertising a book, a frontend or extension read obtains that book through HTTP using its advertised identity rather than resolving it to an unrelated local book.
  • Given an open shared chat, advertised books are accessible through normal lorebook reads but absent from the guest’s lorebook selector and editor.
  • Given shared lorebook access, the addon exposes reads without introducing a shared-book save or change-request mechanism.
  • Given a user leaving a shared chat, that chat’s shared books are no longer available through the frontend’s shared access.
  • Given an owner or guest disconnecting, other viewing frontends retain their already cached lorebooks.
  • Given a successful-save notification for a cached shared book, the viewing frontend fetches the saved contents and replaces its cached version.
  • Given a fetch completing after the user switches chats, its result is discarded without restoring the previous chat’s shared books.
  • Given a confirmed deletion notification for a shared book, the viewing frontend removes its availability and cached contents.
  • Given a failed shared-book refresh with an existing cached version, the frontend reports a load error and retains that version.
  • Given a failed shared-book read without cached contents, the frontend reports a load error and leaves the book unavailable rather than returning an empty book.
  • Given different source accounts advertising books with the same name, qualified reads return the corresponding books and a name-only lookup reports ambiguity.
  • Given one shared book with the same name as a guest’s local book, name-only access within the shared chat resolves to the shared book without modifying the local book, and leaving restores local resolution.
