Shared Conversations

October 29, 2026

Problem

SillyTavern’s native chat handling saves whole transcripts from individual browsers and does not identify human-message authors by account. These mechanisms make it impossible to coordinate contributions from multiple human participants within a single scene.

Participants in a multi-account group chat need to play distinct characters in a shared scene with an AI GM, using a SillyTavern persona to represent each player’s character. The players need to add turns to the chat without triggering an AI response after every message. The account that owns the shared group needs to control when the AI GM responds to the conversation.

All accounts participating in the shared chat need to see the same message history, including edits and deletions. Each player’s messages need to remain attributable to the account that submitted them and the persona that account used to speak.

Solution

This work implements the addon entirely in the frontend/browser. It makes no server-side or Plugin changes.

When a guest is connected to a multiplayer shared chat, its native turn submission, transcript modification, and generation pathways are replaced with coordinated requests using the multiplayer Plugin for communication between browsers.

One connection by an owner is treated as authoritative by the Plugin, and processes those requests through SillyTavern, saving the resulting transcript. Additional owner tabs are treated as guests.

Behavior

Opening a shared chat

When a user opens a shared chat, the addon reports which chat it has loaded to the Plugin and receives the connection’s authority status. On reconnection, the addon reloads the saved chat file without replacing the user’s current composer draft.

A shared chat is active for play only while the owner has it open in a browser connected to the multiplayer Plugin. Different chats can be active in separate owner tabs. Without a connected owner tab viewing the chat, guests can read its stored transcript and compose drafts, but turn submissions, edits, deletions, and AI generation requests are rejected.

Adding a turn to the chat

Sending a human turn adds a user message to the shared chat without automatically requesting an AI response.

The sending user immediately sees the submitted turn with a dashed border and a persistent “Saving…” label. The pending turn cannot be interacted with, and its message controls are visibly disabled. Once saving is confirmed, the turn adopts the normal message appearance and the addon enables the message interactions permitted for that user. Other connections viewing the chat display the new turn after receiving confirmation that it has been saved.

The addon assigns each turn, edit, or deletion request a unique submission identifier and retains it through retries and save confirmations, allowing a pending change to be matched to its saved outcome after reconnection.

The authoritative owner’s addon processes turns, edits, deletions, and generation requests in the order they enter its queue, including locally submitted requests. Each transcript save completes before the addon applies the next queued change.

Identifying the speaker

Each human turn retains SillyTavern’s native message data for the sending user’s persona name and portrait. The addon adds the submitting account’s identifier to the message’s extension metadata, preserving existing message data and metadata from other extensions.

The authoritative owner’s addon records the authenticated submitting account, not the account processing the turn. Changing the sending user’s active persona affects future turns without rewriting the speaker data on earlier messages.

Message controls and permissions

A guest account may edit or delete only messages attributed to that account. The addon hides all message controls on other messages, including AI responses. The owning account may edit only its own messages and AI responses; edit controls are hidden on guest-authored messages. It may delete any message. These permissions also apply when using an additional owner connection.

The owning account retains SillyTavern’s native bulk deletion, which removes the selected message and all messages after it. Guests have only single-message deletion; the addon hides bulk-deletion controls and rejects bulk-deletion requests from guest accounts.

Edits and deletions follow the same submission, queueing, saving, and notification flow as adding a turn to the chat. The authoritative owner’s addon checks edit and deletion requests against these account permissions before applying them.

Requesting an AI turn

The owning account uses SillyTavern’s existing generation controls: Send with an empty composer requests a group response using the group’s configured character-selection rules, and “Trigger a message from this character” requests a response from the selected group member. The addon permits these generation requests only from the owning account.

Generation requests follow the same submission route as human turns. The authoritative owner’s addon runs the requested generation through SillyTavern using the owner’s AI settings.

Displaying the AI response

When SillyTavern streams an AI response, the authoritative owner’s addon sends the live output through the Plugin to the other connections viewing that chat. Each receiving addon updates the same AI message as more text arrives, allowing everyone to follow the response together.

Streamed output remains provisional until its transcript save is confirmed. The saved message replaces the streaming preview rather than appearing as a duplicate. When streaming is disabled, other connections display the generated message after it has been saved.

Player actions during an AI turn

While an AI turn is in progress, all users viewing that chat can continue composing drafts, but the addon disables turn submission, message editing, and message deletion. The authoritative owner’s addon rejects those requests during generation rather than queueing them for later.

Changing the authoritative owner connection

The addon reports when its user leaves a shared chat. If the authoritative owner connection loses its Plugin connection, leaves the chat, or loses its authority assignment, its addon stops generation and stops processing or saving changes for that chat.

On receiving authority, the replacement owner’s addon loads the last saved transcript before telling the Plugin it is ready to process requests. During this handoff, the other users retain their displayed transcript and drafts, but turn submissions, edits, deletions, and generation requests are rejected until the replacement is ready.

Edge Cases

Concurrent edits to the same message
Edits use last-in-wins ordering based on arrival at the authoritative owner’s queue. Each successful edit replaces the saved message text, including when the edit was composed from an earlier version.
A request targets an already-deleted message
Reject an edit with “This message has been deleted” without restoring the message. Treat a repeated deletion as already completed.
The authoritative owner disconnects during AI generation
Remove the unsaved streaming preview, retain the last saved transcript, and show “AI generation interrupted.” A replacement owner connection does not restart generation automatically; the owning account requests another AI turn when ready.
A submitted turn, edit, or deletion fails to save
When saving is confirmed to have failed, keep the affected message visible with “Not saved” and offer Retry and Discard. A failed edit retains the attempted text as unsaved; a failed deletion leaves the message visible. Retry repeats the attempted change. Discard returns the display to the currently saved state, removing a new unsaved turn. Neither action overwrites the user’s current composer draft.
A connection drops before a change’s save confirmation arrives
On reconnection, the addon checks the submission’s status through the Plugin. A saved change is reflected in the displayed transcript without duplication; a change still being processed remains pending; a confirmed unsaved change uses the save-failure treatment above. The addon does not automatically resend a submission whose outcome is uncertain.

Dependencies

The Plugin specification must provide the following capabilities.

  • Authority assignment: identify browser connections by authenticated account, track which chat each connection has loaded, and supply each connection’s authority status. Assign the first owner connection loading a chat as that chat’s sole writing authority and explicitly notify it of the assignment. Connections belonging to guest accounts cannot acquire authority.
  • Request routing: forward turns, edits, deletions, and generation requests from other connections viewing a chat to its authoritative owner connection, including the authenticated submitting account’s identifier.
  • Committed-change notifications: notify the other connected accounts and tabs viewing a chat after a transcript change has been successfully saved. Receipt of a submission alone must not produce a committed-change notification.
  • Submission reconciliation: correlate turn, edit, and deletion requests with their saved outcomes using the addon’s submission identifiers. Report whether a submission is saved, still processing, or confirmed unsaved after reconnection or authority transfer. Repeated submission of the same request must not apply the change more than once.
  • Generation updates: supply the current generation status and notify connections viewing a chat when an AI turn starts and ends, whether or not streaming is enabled. Relay streamed AI output from the authoritative owner connection to the other connections viewing that chat, distinguishing provisional output from committed-change notifications.
  • Authority transfer: when the authoritative connection disconnects or leaves the chat, automatically assign the longest-connected remaining owner connection with that chat loaded and notify it of its authority.
  • Chat readiness: accept confirmation that an assigned owner connection has loaded the saved transcript and is ready to process requests. Inform connections viewing that chat when its writing connection becomes unavailable or ready.

Testing Criteria

Tests run within the addon repository using fake Plugin responses, saved-file fixtures, and substitutes for SillyTavern’s interface, persistence, and generation. They require neither a live Plugin, a multi-account server, nor an AI service.

  • Given a user opening a shared chat, the addon reports that chat to the Plugin and adopts the supplied connection authority status.
  • Given a reconnecting user with an unsent composer draft, the addon reloads the saved chat file without replacing the draft.
  • Given a shared chat without a connected owner, its stored transcript remains readable and drafting remains available, while turn, edit, deletion, and generation requests are rejected.
  • Given separate owner connections assigned to different chats, activity in one chat does not change the other chat’s authority or displayed transcript.
  • Given a human turn submitted from a guest or additional owner connection, the addon forwards the request through the Plugin without independently saving the transcript or running generation.
  • Given a newly submitted human turn awaiting confirmation, only its sending browser displays the pending turn, with a dashed border, “Saving…” label, and disabled message controls.
  • Given remote and local requests arriving at the authoritative owner, they enter the same ordered queue and the next transcript change is not applied before the preceding save completes.
  • Given confirmation that a pending turn was saved, the sending browser displays exactly one saved message with normal appearance and the controls permitted for that account.
  • Given a committed edit or deletion notification, a viewing addon updates or removes the targeted message without independently saving the transcript.
  • Given two distinct change requests and a retry of the first, the distinct requests carry different submission identifiers and the retry retains the first identifier.
  • Given a forwarded human turn containing native persona data and extension metadata, the saved message preserves those values and records the authenticated sender’s account rather than the processing owner or an account claimed in the message payload.
  • Given a user changing their active persona between turns, the later turn uses the new persona while earlier messages retain their stored speaker data.
  • Given a guest requesting an edit or single-message deletion of their own saved message, the authoritative addon applies the permitted change through the ordered save flow.
  • Given a guest viewing a message not attributed to their account, including an AI response, all message controls are hidden and direct edit or deletion requests are rejected without changing the transcript.
  • Given the owning account editing its own message or an AI response, the edit is permitted; a guest-authored message instead has its edit controls hidden and rejects the owner’s edit request.
  • Given the owning account deleting a message authored by any account, the deletion is permitted.
  • Given an owner bulk-deletion request selecting a message, that message and all subsequent messages are removed through the coordinated save flow.
  • Given a guest account, bulk-deletion controls are hidden and a direct bulk-deletion request is rejected without partially deleting the selected range.
  • Given an additional owner connection, owner permissions remain available while change and generation requests are forwarded rather than independently saved or generated.
  • Given the owning account activating Send with an empty composer, the authoritative addon requests native group generation using the owner’s group-selection rules and AI settings.
  • Given the owning account activating “Trigger a message from this character,” the authoritative addon requests a response from the selected group member.
  • Given a guest generation request, no AI generation is started.
  • Given a human turn submitted through Send with text, the turn is processed without automatically starting AI generation.
  • Given successive streamed updates from the authoritative owner, the addon forwards the live output through the Plugin and receiving addons update one provisional AI message rather than appending a message per update.
  • Given save confirmation for a streamed AI message, its saved version replaces the provisional preview without duplication.
  • Given generation with streaming disabled, other viewing connections display the response only after its saved-message notification arrives.
  • Given an AI turn in progress, drafting remains available, turn submission and message editing and deletion are disabled, and directly submitted requests for those changes are rejected rather than queued.
  • Given the authoritative owner connection losing its Plugin connection, leaving the chat, or receiving authority revocation, its addon stops generation and further processing or saving of chat changes.
  • Given a user leaving a shared chat, the addon reports the departure to the Plugin.
  • Given authority assigned to a replacement owner connection, the addon loads the last saved transcript before reporting readiness or processing requests.
  • Given an authority handoff in progress, other viewing browsers retain their transcript and drafts while rejecting turn, edit, deletion, and generation requests until the replacement is ready.
  • Given two edits to the same message, both based on its original text, the later edit in the authoritative queue replaces the earlier saved edit.
  • Given an edit targeting an already-deleted message, the addon reports “This message has been deleted,” restores no message, and leaves any message now occupying the former transcript position unchanged.
  • Given a repeated deletion of an already-deleted message, the request is reported as completed without deleting another message.
  • Given the authoritative owner disconnecting during a streamed AI response, viewers discard the unsaved preview, retain the saved transcript, and see “AI generation interrupted,” without automatic generation by a replacement connection.
  • Given a confirmed failure to save a new turn, edit, or deletion, the affected message remains visible with “Not saved” and Retry and Discard actions; an attempted edit retains its unsaved text.
  • Given Retry on a failed change, the addon resubmits that change without replacing the current composer draft.
  • Given Discard on a failed change, the display returns to the currently saved state, removing a new unsaved turn or restoring the saved state of an edited or deletion-targeted message without replacing the composer draft.
  • Given reconnection after an unconfirmed change, the addon requests the submission’s status rather than automatically resending it.
  • Given a reconciliation response identifying the change as saved, the display reflects that saved outcome without duplicating the message or applying the change again.
  • Given a reconciliation response identifying the change as still processing, its pending state remains.
  • Given a reconciliation response identifying the change as confirmed unsaved, the save-failure controls appear.
