Shared Conversations

October 29, 2026

Problem

SillyTavern’s native chat handling saves whole chats from individual browsers and does not identify human-message authors by account. These mechanisms make it impossible to coordinate contributions from multiple human participants within a single scene.

Participants in a multi-account group chat need to play distinct characters in a shared scene with an AI GM, using a SillyTavern persona to represent each player’s character. The players need to add turns to the chat without triggering an AI response after every message. The account that owns the shared group needs to control when the AI GM responds to the conversation.

All accounts participating in the shared chat need to see the same message history, including edits and deletions. Each player’s messages need to remain attributable to the account that submitted them and the persona that account used to speak.

Solution

This work implements the addon entirely in the frontend/browser. It makes no server-side or Plugin changes.

Guests send turn, edit, and deletion requests through the multiplayer Plugin’s event bus. The selected owner browser performs accepted requests through SillyTavern’s native paths and saves the resulting chat. Its own actions use those same native paths without sending requests through the bus. Additional owning-account tabs are treated as guests.

The addon uses the Server Plugin’s HTTP routes and browser event-bus library. The Plugin supplies transport and owner selection; this frontend feature supplies request handling, pending-change confirmation from saved chats, save notifications, and generation updates.

Behavior

Opening a shared chat

When a user opens a shared chat, the addon uses the Plugin browser library’s join operation and adopts the returned isOwner and ownerPresent values. It handles subsequent changes through bus.status. Owner presence means the chat is ready for play.

The addon uses the Server Plugin’s library lifecycle and reconnection contracts. On bus.disconnected, it disables shared-chat changes while retaining the displayed chat and composer draft; owner-side work and previews follow Changing the authoritative owner connection and the existing interruption outcome. The library handles reconnection and rejoining. After rejoining, the addon adopts the supplied owner status and reloads the saved chat without replacing the draft.

Browsers use SillyTavern’s native loading and rendering paths wherever possible. The selected owner reads and saves its chat through the native group-chat paths. Cross-account chat reads use GET /chats/<accountID>/groups/<groupID>/chats/<chatID>, following the Server Plugin’s contract for that route. Whole chats are loaded over HTTP, not sent through the event bus. Guest loading must not initialize or save a chat, including when the saved chat is empty.

A shared chat is active for play only while the owner has it open in a browser connected to the multiplayer Plugin. Different chats can be active in separate owner tabs. Without a connected owner tab viewing the chat, guests can read its stored chat and compose drafts, but turn submissions, edits, and deletions are rejected and shared-chat generation is unavailable.

Adding a turn to the chat

Sending a human turn adds a user message to the shared chat without automatically requesting an AI response.

The sending user immediately sees the submitted turn with a dashed border and a persistent “Saving…” label. The pending turn cannot be interacted with, and its message controls are visibly disabled. Once saving is confirmed, the turn adopts the normal message appearance and the addon enables the message interactions permitted for that user. Other connections viewing the chat display the new turn after receiving confirmation that it has been saved.

The authoritative owner’s addon coordinates guest requests and local native actions in one ordered queue. Each chat save completes before the addon applies the next queued change or starts generation.

Submission handling

In shared chats, the addon intercepts Send clicks and native keyboard submission shortcuts in the DOM capture phase, before the original submission handlers run. This includes Enter-to-send and Ctrl+Enter with text, which can bypass the Send button. Ordinary chats retain their normal handlers.

The replacement handling runs native command processing first. Input handled as a command is not also submitted as a player turn. For the selected owner’s text turns, the addon uses native user-message preparation, insertion, saving, and rendering without entering the generation flow. Empty-composer Send in that browser retains the native generation path described under Requesting an AI turn.

For guest text turns, the addon assembles the preparation sequence using SillyTavern’s exported native helpers for user-input regexes, macro expansion, bias handling, timestamps, token counting, and attachment preparation. Preparation runs in the guest’s context. The addon captures the prepared message after those operations and any changes they await, displays it as pending separately from the saved chat, and submits it through the send event below without saving locally.

After a native chat save succeeds, the selected owner’s addon sends multiplayer.chat.saved to all with an empty JSON object as its body. This includes saves from local owner actions and AI responses. The event carries no message contents. A failed save produces no saved-change event.

Save confirmation must establish that persistence succeeded. Completion of a native save helper alone is not proof: native saving can report an error locally and still return normally. This applies to saves from message actions, native generation, and addon workflows. A lost save response leaves the outcome uncertain rather than confirming failure.

The selected owner ignores its own event. Other viewing browsers reload the saved chat over HTTP without saving it themselves or replacing their composer drafts. Bus acceptance of a request does not confirm that the change was saved.

The sending browser confirms its pending change from the reloaded chat: a new message is confirmed by finding its extra.multiplayer.messageId, a deletion by that message’s absence, and a player-message edit by matching the attempted replacement text against that message’s current mes value. A later edit from another tab of the same account may supersede the attempted text before confirmation; this is accepted behavior. A matching saved outcome clears the pending display; an unrelated save does not.

The receiving browser matches the event to its pending change using the event name, message identifier, iteration, and replacement text for an edit. A failure from an earlier iteration does not mark the current attempt failed. It applies the “Not saved” treatment under Edge Cases to that change. The selected owner handles failures of its own local actions locally. An uncertain save outcome does not produce a failure event and leaves the change pending.

These events also report rejection before saving: insufficient edit or deletion permission, a shared AI turn in progress, an edit targeting a deleted message, or invalid request data. A deleted edit target uses the reason “This message has been deleted.” Invalid requests receive a failure event when they contain enough identifying information to match the pending action. Rejected requests leave the saved chat unchanged.

Retrying a failed change

All three message-action bodies include iteration, a non-negative integer starting at 0 for each new action and incremented each time the user selects Retry. A new edit or deletion starts at zero even when targeting a previously changed message.

Retry resends the same prepared action through multiplayer.message.send, multiplayer.message.edit, or multiplayer.message.delete. A new turn retains its message identifier and prepared message; an edit retains its target identifier and prepared text; a deletion retains its target identifier. Retry does not replace the composer draft.

Before applying an action with iteration greater than zero, the selected owner checks the saved chat using the confirmation rules under Saved-change event. If those rules already confirm the outcome, it does not apply the action again. Instead, it sends multiplayer.chat.saved directly to the retrying event’s sender.connectionId so that browser reloads the saved chat. Otherwise, it processes the action normally. Local owner retries use the same saved-state checks without sending a bus request.

After a confirmed save failure, the selected owner restores the saved chat before processing further changes. Failed in-memory changes must not be mistaken for saved outcomes or included in a later save. The attempted change remains available in its separate unsaved display for Retry or Discard.

Identifying the speaker

Human turns store their speaker data in the following fields, preserving other native message data and metadata from other extensions.

FieldStored value
nameThe sending user’s persona name when the turn was sent.
force_avatarA portrait URL using the Server Plugin’s Persona image route, GET /accounts/<accountID>/personas/<filename>, under the Plugin’s API mount. The account and image filename identify the sender’s persona portrait when the turn was sent; URL encoding and access follow that route’s contract.
extra.multiplayer.accountIdThe submitting account’s authenticated handle.
extra.multiplayer.messageIdThe message’s stable identifier, stored as a UUID string.

The selected owner takes accountId from the bus-supplied sender for guest requests, or from its authenticated account for local turns, rather than trusting an account claimed in the request body. Changing the sending user’s active persona affects future turns without rewriting the speaker data on earlier messages.

A sending browser assigns a new player message its identifier before submission, so the pending message and its saved version have the same identity. Edits retain that identity; deletions target it rather than a chat position.

New AI messages receive identifiers before their first preview or save, including responses generated without streaming. A newly generated swipe retains the message’s identifier in its swipe_info entry’s extra.multiplayer.messageId, so native swipe selection preserves the identity of the message.

Message controls and permissions

Only the selected owner browser may edit AI responses, delete messages authored by other accounts, or use bulk deletion. It may edit its own account’s player messages but not other accounts’ player messages; edit controls are hidden on those messages.

Every other browser, including additional tabs from the owning account, may edit or single-delete only player messages attributed to its authenticated account. The addon hides all message controls on other messages, including AI responses. The selected owner applies these restrictions to every incoming bus request, including requests from its own account.

The selected owner retains SillyTavern’s native bulk deletion, which removes the selected message and all messages after it. Every other browser has bulk-deletion controls hidden, and the selected owner rejects all bulk-deletion requests received through the bus.

Edits and deletions follow the same submission, queueing, saving, and notification flow as adding a turn to the chat. The authoritative owner’s addon checks edit and deletion requests against these account permissions before applying them.

Editing a player message appends the revised text to its native swipes array and selects the new swipe, preserving earlier versions, including the original text. This applies both to the selected owner’s local edits and to edits it performs for other browsers. Swipes need no separate stable identifier. The selected owner’s local edits to AI responses retain SillyTavern’s native in-place behavior.

Player-message swipe metadata

The addon initializes player-message swipe data because SillyTavern’s native swipe initializer skips user messages. Before the first edit of a player message without swipe history, it sets swipes to an array containing the original text, swipe_id to 0, and swipe_info to an array containing the original version’s metadata entry.

Each edit appends a metadata entry to swipe_info at the same index as its new text in swipes. Existing entries remain intact. Each entry contains:

FieldValue
send_dateThe original message timestamp. Editing does not change when the turn was sent.
extraAn independent copy of that version’s message metadata, including multiplayer.accountId and multiplayer.messageId. Metadata objects are not shared between revisions.

Human edits do not add AI generation timestamps. Selecting a player-message swipe restores its text and metadata together, retaining the message’s identity and account attribution.

Requesting an AI turn

Only the selected owner browser can start shared-chat generation, using SillyTavern’s existing controls and the owner’s AI settings. Send with an empty composer requests a group response using the group’s configured character-selection rules, and “Trigger a message from this character” requests a response from the selected group member.

Generation that adds or revises shared conversation messages is disabled in every other browser, including additional tabs from the owning account. Shared-chat generation starts locally through the selected owner’s native paths; there is no bus request to start it.

Addon generation and draft assistance

Generation and revision workflows from addons such as inSTead and Guided Generation run only in the selected owner browser. In other browsers, the multiplayer addon makes a best effort to disable known addon controls that generate or revise shared conversation messages by hiding them and intercepting their activation, including controls added dynamically.

Private draft assistance remains available to guests, including Guided Generation’s Guided Impersonate actions. These use the guest browser’s configured generation settings and place their result in its composer without changing the shared chat. The result remains a draft until the guest submits it through the normal shared-turn flow.

Player actions during an AI turn

While a shared AI turn is in progress, all users viewing that chat can continue composing drafts, but the addon disables turn submission, message editing, and message deletion. The authoritative owner’s addon rejects those requests during generation rather than queueing them for later.

Changing the authoritative owner connection

The addon uses the Plugin browser library’s leave operation when its user leaves a shared chat. If the authoritative owner receives bus.disconnected, leaves the chat, or loses its authority assignment through bus.status, its addon stops shared-chat generation and stops processing or saving changes for that chat.

On receiving authority, the replacement owner’s addon requests the chat again through SillyTavern’s native loading path. Other users retain their displayed chat and drafts and use the Plugin’s owner-presence status.

The addon handles the Server Plugin’s server-originated multiplayer.owner.changed event when the selected owner leaves or disconnects, including when an immediate replacement keeps owner presence true. Viewers discard unsaved AI previews and clear the previous owner’s generation status. If an owner remains present, they request its current generation status through multiplayer.generation.status_request. This introduces no readiness handshake or additional delivery guarantee.

Edge Cases

Concurrent edits to the same message
Edits use last-in-wins ordering based on arrival at the authoritative owner’s queue, including when composed from an earlier version. For player messages, each edit adds a swipe and the latest edit becomes selected; earlier revisions remain in the swipe array. AI-response edits replace the text in place.
A request targets an already-deleted message
Reject an edit with “This message has been deleted” without restoring the message. Treat a repeated deletion as already completed.
The authoritative owner disconnects during AI generation
Remove the unsaved streaming preview, retain the last saved chat, and show “AI generation interrupted.” A replacement owner connection does not restart generation automatically; the selected owner requests another AI turn when ready.
A submitted turn, edit, or deletion is rejected or fails to save
When a request is rejected or saving is confirmed to have failed, keep the affected message visible with “Not saved” and offer Retry and Discard. A failed edit retains the attempted text as unsaved; a failed deletion leaves the message visible. Retry follows Retrying a failed change. Discard returns the display to the currently saved state, removing a new unsaved turn. Neither action overwrites the user’s current composer draft.
A connection drops before a change’s save confirmation arrives
On reconnection, the addon reloads the saved chat and checks pending changes using the confirmation rules under Saved-change event. Confirmed changes clear their pending display without being applied again. Unconfirmed changes remain pending and are not automatically resent. An uncertain outcome is not a save failure; “Not saved” requires an explicit failure.

Testing Criteria

Tests run within the addon repository using fake Plugin responses, saved-file fixtures, and substitutes for SillyTavern’s interface, persistence, and generation. They require neither a live Plugin, a multi-account server, nor an AI service.

Opening chats and connection lifecycle

  • Given a user opening a shared chat, the addon joins through the Plugin’s browser library and adopts the returned isOwner and ownerPresent values.
  • Given bus.status for the open chat, the addon updates its authority and treats owner presence as readiness.
  • Given a reconnecting user with an unsent composer draft, the addon reloads the saved chat file without replacing the draft.
  • Given a shared chat without a connected owner, its stored chat remains readable and drafting remains available, while turn, edit, and deletion requests are rejected and shared-chat generation is unavailable.
  • Given a cross-account chat load, the addon uses the Plugin’s chat HTTP route and native rendering without requesting a whole chat through the bus.
  • Given a guest loading an empty saved chat, the addon does not initialize or save the chat.
  • Given a selected owner loading or saving its chat, the addon uses SillyTavern’s native group-chat paths.
  • Given separate owner connections assigned to different chats, activity in one chat does not change the other chat’s authority or displayed chat.

Turn submission and saving

  • Given a human turn submitted from a guest or additional owner connection, the addon sends multiplayer.message.send to owner with the body’s message and iteration fields, without independently saving the chat or running generation.
  • Given Send or an enabled native keyboard submission shortcut in a shared chat, the addon intercepts submission before the original handler runs; ordinary chats retain their original submission behavior.
  • Given input consumed by native command processing, the replacement submission handling does not also submit it as a player turn.
  • Given a local text turn from the selected owner, native user-message preparation, insertion, saving, and rendering run without entering generation.
  • Given a guest turn, native preparation helpers run in the guest’s context before the prepared message is captured and sent.
  • Given an accepted prepared guest turn, the owner preserves its text, timestamp, and other metadata without rerunning the owner’s send-time transformations or attachment preparation.
  • Given a malformed multiplayer.message.send body or message with invalid user-message flags, the owner leaves the chat unchanged.
  • Given a newly submitted human turn awaiting confirmation, only its sending browser displays the pending turn, with a dashed border, “Saving…” label, and disabled message controls.
  • Given guest requests and local native actions arriving at the selected owner, they enter the same ordered queue and the next chat change or generation does not start before the preceding save completes.
  • Given a local action in the selected owner browser, it uses the native paths without sending an action request through the bus.
  • Given a successful native chat save, the selected owner sends multiplayer.chat.saved to all with an empty JSON object body; a failed save produces no such event.
  • Given a native save helper that returns normally after reporting a save error, the addon does not treat that return as save confirmation or publish a saved-change event.
  • Given a lost save response, the addon treats the outcome as uncertain rather than publishing a saved-change or confirmed-failure event.
  • Given the selected owner receiving its own multiplayer.chat.saved event, it does not reload the chat.
  • Given confirmation that a pending turn was saved, the sending browser displays exactly one saved message with normal appearance and the controls permitted for that browser.
  • Given multiplayer.chat.saved, another viewing browser refreshes the chat over HTTP and reflects the saved change without saving it or replacing the composer draft.

Message identity, attribution, and confirmation

  • Given a new player message, its pending and saved versions retain the same UUID string in extra.multiplayer.messageId.
  • Given a new AI message, the selected owner assigns its identifier before the first preview or save, including when streaming is disabled.
  • Given a newly generated AI swipe, its swipe_info entry retains the message’s extra.multiplayer.messageId, and selecting that swipe preserves the message identifier.
  • Given a reloaded chat containing a pending new message’s identifier, the sender clears that message’s pending state.
  • Given a reloaded chat without a pending deletion’s message identifier, the sender clears that deletion’s pending state.
  • Given a reloaded player message whose current mes matches the pending edit’s attempted replacement text, the sender clears that edit’s pending state. A match only in historical swipes does not confirm the edit.
  • Given a reload that does not contain the pending change’s saved outcome, that change remains pending.
  • Given a forwarded human turn, the saved message records the bus-supplied sender’s authenticated handle in extra.multiplayer.accountId, rather than the processing owner or an account claimed in the body, while preserving other native fields and extension metadata.
  • Given a local human turn from the selected owner, extra.multiplayer.accountId records its authenticated account handle.
  • Given a human turn with a persona name and portrait, the saved message stores the name in name and a Plugin Persona image URL qualified by the sender’s account and image filename in force_avatar.
  • Given a user changing their active persona between turns, the later turn uses the new persona while earlier messages retain their stored speaker data.

Message controls and permissions

  • Given a guest requesting an edit or single-message deletion of their own saved message, the authoritative addon applies the permitted change through the ordered save flow.
  • Given an edit from a browser other than the selected owner, the addon sends multiplayer.message.edit to owner with the stable messageId, native-prepared replacement text, and iteration.
  • Given an accepted player-message edit event, the owner appends the prepared text to swipes, selects its index in swipe_id, and updates mes without repeating edit-time text processing.
  • Given a local owner edit, no multiplayer.message.edit event is sent.
  • Given a guest viewing a message not attributed to their account, including an AI response, all message controls are hidden and direct edit or deletion requests are rejected without changing the chat.
  • Given the selected owner editing its own account’s player message or an AI response locally, the edit is permitted; another account’s player message instead has its edit controls hidden and rejects the edit.
  • Given the selected owner deleting a message authored by any account locally, the deletion is permitted.
  • Given the selected owner using native bulk deletion locally, the selected message and all subsequent messages are removed through the coordinated save flow.
  • Given a deletion from a browser other than the selected owner, the addon sends multiplayer.message.delete to owner with the stable messageId and iteration.
  • Given an accepted deletion event, the selected owner deletes only the message resolved by its stable identifier.
  • Given a local owner deletion, no multiplayer.message.delete event is sent.
  • Given any browser other than the selected owner, bulk-deletion controls are hidden and a direct bulk-deletion request is rejected without partially deleting the selected range.
  • Given an additional owning-account connection, it has the same permissions as other guest browsers: edit or single-delete only its authenticated account’s player messages, with shared-chat generation disabled.
  • Given an AI-response edit request through the bus, including from the owning account, the selected owner rejects it without changing the message.

Generation controls and draft assistance

  • Given the selected owner activating Send with an empty composer, native group generation uses the owner’s group-selection rules and AI settings without a bus request.
  • Given the selected owner activating “Trigger a message from this character,” native generation requests a response from the selected group member without a bus request.
  • Given any browser other than the selected owner, native shared-chat generation controls are disabled and attempts through those controls produce no shared-chat generation.
  • Given known addon controls that generate or revise shared conversation messages in a guest browser, the addon disables those controls while leaving private draft assistance available.
  • Given a guest using Guided Impersonate, its result remains in that browser’s composer without submitting a turn or saving the shared chat.
  • Given a guest submitting an assisted draft, it follows the same shared-turn flow as manually composed text.
  • Given a human turn submitted through Send with text, the turn is processed without automatically starting AI generation.

Generation previews and status

  • Given a streamed AI response update, the selected owner sends multiplayer.generation.preview to all with messageId, name, force_avatar, and accumulated response text.
  • Given successive preview events with the same message identifier, other browsers replace the text of one provisional message rather than appending tokens or another message.
  • Given the selected owner receiving its own preview event, it leaves its native response display unchanged.
  • Given a model reasoning stream, it is not included in preview events.
  • Given a saved chat reload containing a streamed AI message’s identifier, its saved version replaces the provisional preview without duplication.
  • Given generation with streaming disabled, the owner sends no preview events and other viewing connections display the response after the saved-change event triggers a chat reload.
  • Given a shared AI turn in progress, drafting remains available, turn submission and message editing and deletion are disabled, and directly submitted requests for those changes are rejected rather than queued.
  • Given a shared AI turn starting, the selected owner sends multiplayer.generation.status to all with generating: true, including when streaming is disabled.
  • Given a shared AI turn finishing, stopping, or failing, the selected owner publishes generating: false.
  • Given a group turn producing multiple character responses, generation status remains true between those responses until the whole turn ends.
  • Given a non-owner browser joining or reconnecting with an owner present, it sends multiplayer.generation.status_request to owner with an empty JSON object body.
  • Given a generation-status request, the selected owner answers with its current status through multiplayer.generation.status to all.
  • Given a received generation status, the browser updates turn-submission, edit, and deletion availability without replacing the composer draft.
  • Given private draft assistance, no shared generation-status change is published for that operation.

Owner changes and reconnection

  • Given the authoritative owner connection losing its Plugin connection, leaving the chat, or receiving authority revocation, its addon stops shared-chat generation and further processing or saving of chat changes.
  • Given a user leaving a shared chat, the addon invokes the Plugin browser library’s leave operation.
  • Given bus.disconnected, the addon disables shared-chat changes while retaining the displayed chat and composer draft, applying the existing interruption rules to owner-side work and unsaved previews.
  • Given reconnection, the addon relies on the library to rejoin, then adopts the supplied owner status and reloads the saved chat without replacing the draft.
  • Given authority assigned to a replacement owner connection, the addon reloads the chat through the native path.
  • Given an owner replacement, other viewing browsers retain their chat and drafts and use the Plugin’s owner-presence status.
  • Given a server-originated multiplayer.owner.changed event, viewers discard unsaved AI previews and clear the previous owner’s generation status, including when owner presence remains true through an immediate replacement.
  • Given an owner-change event with an owner remaining present, viewers request its current generation status through multiplayer.generation.status_request.

Revision history, deleted targets, and interrupted generation

  • Given a player-message edit, whether local to the selected owner or requested by another browser, the addon appends and selects a new swipe while preserving the message identifier and earlier versions, including the original text.
  • Given two edits to the same player message, both based on its original text, both revisions remain as swipes and the later edit in the authoritative queue is selected.
  • Given a player message without swipe history, its first edit initializes the original text and metadata at index zero before appending the revision.
  • Given a player-message revision, its swipe_info entry occupies the same index as its text, retains the original send_date, and contains an independent copy of that version’s extra without adding AI generation timestamps.
  • Given a change to one revision’s metadata, other revisions’ metadata remains unchanged.
  • Given selection of a player-message swipe, its text and metadata are restored together without losing extra.multiplayer.messageId or extra.multiplayer.accountId.
  • Given a local selected-owner edit to an AI response, the addon retains native in-place editing rather than appending a revision swipe.
  • Given an edit targeting an already-deleted message, the addon reports “This message has been deleted,” restores no message, and leaves any message now occupying the former chat position unchanged.
  • Given a deletion event targeting an already-deleted message, the owner deletes nothing, performs no new save, and sends multiplayer.chat.saved directly to the requester so it can reload and confirm completion.
  • Given the authoritative owner disconnecting during a streamed AI response, viewers discard the unsaved preview, retain the saved chat, and see “AI generation interrupted,” without automatic generation by a replacement connection.

Failures, retries, and uncertain outcomes

  • Given a confirmed failure to save a new turn, edit, or deletion, the affected message remains visible with “Not saved” and Retry and Discard actions; an attempted edit retains its unsaved text.
  • Given a confirmed save failure for a remote message submission, the selected owner sends multiplayer.message.send_failure directly to that request’s sender.connectionId with messageId, iteration, and a human-readable reason.
  • Given a confirmed save failure for a remote edit, the selected owner sends multiplayer.message.edit_failure directly to that request’s sender.connectionId with messageId, attempted text, iteration, and a human-readable reason.
  • Given a confirmed save failure for a remote deletion, the selected owner sends multiplayer.message.delete_failure directly to that request’s sender.connectionId with messageId, iteration, and a human-readable reason.
  • Given a save-failure event matching a pending change by event name, message identifier, iteration, and replacement text for an edit, the requesting browser applies “Not saved” to that change.
  • Given a failure reply, it echoes the rejected or failed request’s iteration.
  • Given a failure event from an earlier iteration, the requesting browser does not mark its current attempt failed.
  • Given a save failure for a local owner action, the owner applies the failure treatment locally without sending itself a failure event.
  • Given an uncertain save outcome, the owner sends no save-failure event and the requesting browser retains the pending state.
  • Given a request rejected for insufficient permissions or because shared generation is in progress, the owner sends the action-specific failure event directly to the requester with an explanatory reason and leaves the saved chat unchanged.
  • Given an edit request targeting a deleted message, the owner replies with multiplayer.message.edit_failure and the reason “This message has been deleted.”
  • Given invalid request data with enough identifying information to match a pending action, the owner sends the action-specific failure event with an explanatory reason without changing the saved chat.
  • Given an action-failure event reporting rejection before saving, the requesting browser applies the same “Not saved” treatment as for a confirmed save failure.
  • Given a repeated deletion of an absent message, the owner does not report that absence as a deletion failure.
  • Given a new turn, edit, or deletion action, its body includes iteration: 0, even when its target was changed before.
  • Given Retry on a failed turn, edit, or deletion, the addon increments iteration and resends the same prepared action through its original event, retaining its message identifier and any prepared content without replacing the composer draft.
  • Given a retried action whose outcome is already confirmed in the saved chat, the owner does not apply it again and sends multiplayer.chat.saved directly to the retrying request’s sender.connectionId.
  • Given a retried action whose outcome is not confirmed in the saved chat, the owner processes it through the normal action flow.
  • Given Retry for a local owner action, the owner checks saved state without sending a bus request.
  • Given a confirmed save failure, the owner restores the saved chat before processing another change while retaining the attempted change separately for Retry or Discard.
  • Given Discard on a failed change, the display returns to the currently saved state, removing a new unsaved turn or restoring the saved state of an edited or deletion-targeted message without replacing the composer draft.
  • Given reconnection after an unconfirmed change, the addon reloads the saved chat and checks for its saved outcome without sending a submission-status query or automatically resending the change.
  • Given a reconnect reload confirming a pending change under the saved-state confirmation rules, its pending display clears without applying the change again.
  • Given a reconnect reload that does not confirm a pending change, that change remains pending rather than being marked “Not saved.”
