Server Plugin

October 30, 2026

Problem

SillyTavern users playing together in a shared multiplayer group chat need access to the same scene resources and conversation history across separate accounts. Their browsers and addons need to exchange messages to coordinate activity in that shared chat.

SillyTavern currently isolates those resources by account and provides no communication mechanism between participating browsers.

Solution

The multiplayer addon includes its server plugin and browser event-bus library as parts of one project. The server plugin provides two components:

  • HTTP router: exposes two resource route families. /accounts provides account discovery and authorized access to character cards, portraits, and lorebooks nested under their source account. /chats provides shared-group discovery, group details, chat listings, and chat transcripts. Resource identities include their source account to distinguish matching names or IDs.
  • Event bus: carries messages from clients to the server, which routes them to other clients. Multiplayer features use this transport; message meaning and the actions triggered belong to its consumers.

The session-owning browser remains responsible for AI generation and authoritative frontend workflows.

Behavior

HTTP conventions

Paths below are relative to the plugin’s API mount. The resource routes below are GET requests with no request body. JSON responses use application/json. Account identity comes from the native authenticated session, not a caller-supplied identity. Route identifiers select resources, not filesystem paths; they cannot escape their source account’s resource directory.

Account listing — GET /accounts

For an authenticated caller, return an array of enabled accounts whose “Allow others to add me to shared groups” setting is enabled. Read this preference from each account’s native extension settings; an absent preference means enabled. Discreet login does not affect this listing. Include the requesting account when it meets the same eligibility rules; the addon handles filtering.

Each record contains only the following fields:

Event bus

The event bus uses WebSocket to carry client messages through the server to recipient clients.

Attaching to the SillyTavern server

SillyTavern supplies the plugin with an HTTP router rather than the listening server. During the authenticated ticket request, the plugin obtains the underlying HTTP or HTTPS server from the request’s socket and attaches a WebSocket upgrade listener to that server. The bus shares SillyTavern’s existing listener and port, without a separate server or changes to SillyTavern core.

Attach at most once per underlying server instance, before returning a connection ticket. Handle only upgrades for this plugin’s /events path; leave other upgrade paths to their existing handlers. Upgrade requests bypass the normal HTTP middleware, so connection authentication uses the ticket contract below. Plugin shutdown removes its upgrade listeners and closes its WebSocket connections.

On an authenticated ticket request:
    Obtain the listening server from the request’s socket
    If this plugin has not attached to that server:
        Attach an upgrade listener scoped to this plugin’s event path
    Issue the connection ticket

On an upgrade for this plugin’s event path:
    Validate the connection ticket
    Accept the WebSocket and consume the ticket
    Associate the connection with the ticket’s authenticated account

Connection authentication

An authenticated, CSRF-protected POST /events/connect issues a short-lived, single-use ticket bound to the authenticated account. The browser library presents that ticket to open a WebSocket at /events on the existing SillyTavern server. These paths are relative to the plugin’s API mount.

The ticket request has no body. Tickets expire 30 seconds after issuance and are consumed on successful connection. The library presents the ticket in the WebSocket URL’s ticket query parameter. The plugin must not log ticket values.

Response fieldValue
ticketThe single-use connection ticket.
expiresAtTicket expiry as an ISO 8601 UTC timestamp.
StatusOutcome
200The ticket request succeeded; return the ticket response.
403The ticket request is unauthenticated or fails CSRF validation.
500The ticket could not be issued.

The WebSocket upgrade returns 101 on success. A missing, expired, or previously consumed ticket rejects the upgrade with 403.

Connection health

The server sends a native WebSocket ping every 15 seconds; the browser responds with a native pong without library or addon handlers. If its pong does not arrive within 15 seconds, terminate the connection. A closed or terminated connection is removed from its Chat, applying the owner-reselection and Chat-removal rules below.

Reconnection

The browser library automatically reconnects using a fresh ticket and connection identity. Retry after 1, 2, 4, 8, and then 15 seconds, keeping subsequent retries at 15 seconds. Stop retrying when ticket issuance returns 403. A successful connection resets the retry delay.

On reconnection, the browser library joins the currently open chat, not a remembered previously joined chat; it joins none if no chat is open. It does not resend messages.

Browser library

The browser library ships with the multiplayer addon and exposes connect, send, handler registration and unsubscription, join, and leave operations. It is the foundation used by multiplayer itself and other consuming addons, rather than each implementing the WebSocket protocol separately. This specification defines the library and server contracts together; application workflows belong to the consuming addons.

Send, join, and leave return promises resolved by the matching server acknowledgment or rejected on failure. Join resolves with isOwner and ownerPresent; send and leave resolve without a value. Handler registration is synchronous and returns its unsubscribe function.

Library lifecycle events

Addons subscribe to library lifecycle events through the same handler-registration API. These reserved events cannot be sent through the application send operation. Their sender is null. Connection lifecycle events without chat context also have a null chat argument; bus.status carries the chat identity from its status envelope.

EventMeaning
bus.connectedThe WebSocket connection has opened. The body is null.
bus.disconnectedThe WebSocket connection has closed or been lost. The body is null.
bus.statusThe server supplied session status; the body contains isOwner and ownerPresent.

In-memory Chat

The server maintains a Chat record distinct from the saved transcript:

FieldMeaning
IdentityOwning account, group ID, and chat ID.
Connected clientsConnection identities and their authenticated accounts.
Session-owner connectionThe connection targeted by owner, or none.
Connection orderingThe ordering needed to select a replacement session-owner connection.

Create the record when the first client joins. Remove it when the last client leaves or disconnects, without changing stored groups or transcripts. Guest connections can keep the record alive without a session-owner connection.

The owning account is the account storing the group. The first connection from that account joining the chat becomes its session-owner connection. Additional connections from the owning account remain ordinary recipients. When the session-owner connection leaves or disconnects, select the longest-connected remaining connection from the owning account viewing that chat. Connections from guest accounts cannot become session owner.

The Chat record remains server-side. A successful join returns isOwner and ownerPresent booleans in its response data. The former identifies session ownership by this connection; the latter indicates that a session-owner connection exists. Subsequent changes use the status envelope defined in Wire format. Clients do not receive the Chat record.

Readiness messages are application events carried by the bus; the server’s routing status does not represent application readiness.

Connection context

A client explicitly joins a chat by supplying its owning account, group ID, and chat ID. The server checks that the authenticated account owns or participates in the group and that the chat belongs to that group. Each connection belongs to at most one chat. Join and leave operations take effect in arrival order per connection. Validate a join before changing the association: a failed join leaves the previous association intact, and a successful join replaces it. Joining the same chat again succeeds without changing owner selection. Leaving clears the association and succeeds even when no chat is joined.

Message types and handlers

Any addon can send its own namespaced message types through the bus using the destinations above. Message types use an addon namespace followed by a period and an event name, such as multiplayer.turn or rpg-companion.update.

Receiving addons register client-side handlers for message types. The server routes messages without requiring a server-side handler or interpreting their meaning. A receiving client with no registered handler for a type ignores that message.

Multiplayer messages use the same registration and delivery mechanism as messages from any other addon.

Registering a handler

The client-facing registration operation accepts the event name and a handler, and returns an unsubscribe function that removes that registration. Multiple handlers may register for the same event name without replacing one another. Each handler receives three arguments: chat identity, sender, and body. Each handler receives its own independent deep copy of those values. Mutating that copy cannot affect another handler’s input.

Sending a message

The client-facing send operation accepts three positional arguments:

ArgumentValue
Destinationowner or all.
Event nameThe namespaced message type.
Event bodyThe JSON payload delivered to handlers.

The chat is derived from the connection’s currently loaded chat, and the sender from authentication; neither is supplied as a send argument.

Delivery

The bus delivers live messages to currently connected recipients. It maintains no offline backlog and does not automatically replay messages after reconnection. Submission-status messages use the ordinary event transport rather than transport replay.

A successful send confirms only that the server accepted the message for routing, not that recipients handled it. Features requiring a result send a response event. Sending fails immediately rather than waiting or queueing when the client is disconnected, has no chat loaded, or targets owner without a connected session owner.

Messages from each sender are delivered in send order. Listeners are invoked in registration order without waiting for asynchronous handlers to finish. Synchronous exceptions and asynchronous rejections are logged locally without preventing other handlers from receiving the event. Features requiring sequential completion manage their own queues.

If the connection drops before a request’s acknowledgment arrives, the library rejects the outstanding request with an explicit unknown-outcome error. It does not claim that the request was undelivered and does not automatically retry it.

Wire format

Messages use JSON envelopes. Client requests identify their operation as join, leave, or send and include a request ID. Each request receives a success or error response correlated by that ID. Request IDs provide correlation only, not replay or deduplication.

Send requestop: "send", requestId, destination, eventName, body.
Responseop: "result", requestId, ok, and data on success or error on failure. Successful send and leave responses use data: null.
Delivered eventop: "event", chat, eventName, sender, body.

Error responses

An error response contains an error object with a machine-readable code and human-readable message. Authorization takes precedence over resource existence.

CodeMeaning
invalid_requestMalformed envelope or unsupported operation.
forbiddenThe authenticated account lacks access to the requested chat.
not_foundAn authorized resource is missing.
not_joinedSending without a joined chat.
owner_unavailableSending to owner when no session owner exists.
internal_errorThe server could not complete the request.

Validation

The bus treats each message body as opaque JSON and forwards it unchanged, without body schemas or central body validation. Each receiving handler decides what body contents it accepts.

The bus validates the routing envelope: a namespaced message type, one of the supported destinations, and a shared chat in which the sender participates. It supplies the authenticated sender identity rather than trusting an identity claimed in the body.

Edge Cases

Authentication is restored after a 403 stopped reconnection
The library exposes an explicit connect operation that restarts connection attempts without requiring a page refresh. Calling it while already connected does nothing.
A message body cannot be serialized as JSON
The library rejects the send locally, transmits nothing, and leaves the connection open. This includes circular objects and unsupported values such as BigInt.
An event or status arrives for a previously open chat
The library compares the envelope’s chat identity with the currently open chat. Drop a mismatched event or status without invoking handlers or updating session status.
A join is superseded by a newer join or leave
The most recent join or leave intent wins. Reject the superseded join’s promise with a superseded error and drop its late acknowledgment without changing current status or emitting bus.status. The library’s final association follows the latest intent.
Malformed WebSocket message
Reject malformed JSON or an invalid envelope with invalid_request, keeping the connection open and Chat state unchanged. Return the request ID when usable; otherwise return requestId: null.

Testing Criteria

Tests run within this project using storage fixtures, fake authenticated requests, simulated connections and browser context, and controlled clocks. They require neither a live SillyTavern installation nor another service.

HTTP resources

  • Given enabled accounts with enabled, disabled, and absent discoverability preferences, the account listing includes only enabled accounts with enabled or absent preferences, including the requester when eligible, regardless of discreet login.
  • Given eligible account fixtures, account records contain only id, name, and avatar, with an image data URL for a configured avatar and null when unset.
  • Given an unauthenticated resource request, the route returns 403.
  • Given a requester without access to a named resource, the route returns 403 whether or not that resource exists.
  • Given authorized access and a missing resource, the resource route returns 404 rather than empty content.
  • Given a required resource that cannot be read or parsed, the route returns 500 rather than empty or partial content.
  • Given a route identifier attempting to escape the source resource directory, no file outside that directory is read or returned.
  • Given authorized resources with identical names or IDs in different accounts, each qualified route returns only its selected source account’s resource.
  • Given a group containing a character and the requesting participant, the character-card route returns the native card JSON and the character-image route returns the unchanged PNG, including embedded metadata, with image/png content type.
  • Given a character absent from every group shared with the requester, its card and image routes return 403.
  • Given accounts sharing a group and a known persona-image filename, the persona route returns the original image with its image content type even when it is not the source account’s active persona.
  • Given accounts sharing a group and a known lorebook filename, the lorebook route returns the complete saved JSON, including disabled entries, without consulting an advertised-book registry.
  • Given accounts with no shared group, cross-account persona-image and lorebook reads return 403.
  • Given authorized resource requests without any connected owner browser, their results are unchanged by the absence of that connection.
  • Given owned groups, participating groups, and unrelated groups, the cross-account group listing returns only owned and participating groups with owner.id/owner.name and native group JSON.
  • Given accessible groups from multiple source accounts, the account-specific group listing returns only those belonging to its requested source account.
  • Given no eligible accounts or no accessible groups, the corresponding collection route returns 200 with an empty array.
  • Given an accessible group, its detail route returns the same owner/group structure as its collection entry, including native chat IDs and account membership.
  • Given a group with stored chat IDs, its chat collection returns native summary records in that stored order and includes no unrelated owner-account chats.
  • Given a group with no chat IDs, its chat collection returns 200 with an empty array.
  • Given a group referencing a missing or unreadable chat file, the chat collection returns 404 or 500 respectively instead of a partial listing.
  • Given an authorized chat transcript, its route returns a JSON array in file order preserving the metadata header and every message and extension field.
  • Given an existing empty transcript file, the transcript route returns 200 with an empty array.
  • Given a requested chat ID absent from the selected group, the transcript route returns 403 even if that chat exists elsewhere.
  • Given a successful JSON resource response, its content type is application/json.

Connection establishment and recovery

  • Given repeated authenticated ticket requests through one underlying server instance, the plugin attaches exactly one upgrade listener to that instance before issuing tickets.
  • Given a WebSocket upgrade for another path, the plugin’s listener leaves it untouched.
  • Given plugin shutdown, its upgrade listeners are removed and its WebSocket connections are closed.
  • Given an authenticated, CSRF-valid ticket request without a body, the route returns 200 with a single-use ticket bound to that account and an ISO 8601 UTC expiresAt value 30 seconds after issuance.
  • Given an unauthenticated or CSRF-invalid ticket request, the route returns 403 and issues no ticket.
  • Given a ticket-issuance failure, the route returns 500.
  • Given an unexpired ticket presented to the WebSocket endpoint, the upgrade returns 101 and consumes the ticket.
  • Given a missing, expired, or consumed ticket, the upgrade returns 403.
  • Given ticket issuance and connection attempts, plugin logs contain no ticket values.
  • Given an open connection and a controlled clock, the server sends native WebSocket pings at 15-second intervals without generating application heartbeat events.
  • Given a ping with no pong within 15 seconds, the connection is terminated and removed from its Chat.
  • Given a lost connection and repeated network failures, the library retries after 1, 2, 4, 8, and 15 seconds, then continues indefinitely at 15-second intervals.
  • Given a successful reconnection, the library uses a fresh ticket and connection identity and resets its retry delay.
  • Given ticket issuance returning 403 during reconnection, automatic retries stop.
  • Given stopped retries followed by an explicit connect operation after authentication is restored, connection attempts resume without a page refresh.
  • Given an already connected library, an explicit connect operation creates no additional connection.
  • Given a changed currently open chat during an outage, reconnection joins that current chat rather than the previously joined chat; with no open chat, it joins none.
  • Given messages sent before a disconnection, reconnection neither resends them nor replays missed events.
  • Given a connection dropping before acknowledgment, the outstanding request rejects with an unknown-outcome error rather than an undelivered result or an automatic retry.

Chat membership and session ownership

  • Given the first valid join for a chat, the server creates its in-memory Chat record independently of stored transcript content.
  • Given a join from an account without group access or for a chat outside the group, the server rejects it without changing the connection’s previous association.
  • Given join and leave requests on one connection, their effects occur in arrival order.
  • Given a successful join to a different chat, the connection belongs only to the newly selected chat.
  • Given a repeated join to the same chat, the request succeeds without changing owner selection.
  • Given a leave request, the association is cleared; leaving an already unjoined connection also succeeds.
  • Given the first owning-account connection joining a chat, it becomes session owner while subsequent owning-account connections remain ordinary recipients.
  • Given only guest-account connections in a chat, no connection acquires session ownership and the Chat record remains present.
  • Given a departing session owner and remaining owning-account connections, the longest-connected eligible connection is selected as replacement.
  • Given the last connection leaving or disconnecting, the server removes the Chat record without changing stored groups or transcripts.
  • Given connections in distinct chats, joins, departures, and owner selection in one chat do not alter the other chat.
  • Given a successful join, its result reports isOwner for that connection and ownerPresent for the session, without exposing the server’s Chat record.
  • Given a change to a connection’s owner-status facts, the server sends a status envelope with the chat identity and updated booleans.
  • Given a join superseded by a newer join or leave, its promise rejects as superseded and its late acknowledgment produces neither a current-status update nor bus.status.
  • Given an event or status envelope for a previously open chat, the library drops it without invoking handlers or updating current session status.

Routing and protocol

  • Given a valid send to owner, only the selected session-owner connection receives the event, including when that connection is also the sender.
  • Given a valid send to all, every connection joined to that chat receives the event, including the sender, and connections in other chats receive none.
  • Given a disconnected sender, an unjoined sender, or an owner destination without a session owner, sending fails rather than waiting or queueing.
  • Given an addon-defined namespaced event with a JSON body, the server routes it without requiring a registered server-side handler or body schema.
  • Given a body containing a claimed sender identity, the delivered envelope still identifies the authenticated account and actual sending connection while preserving the body unchanged.
  • Given a routed event or status, its chat object contains the owning accountId, groupId, and chatId.
  • Given multiple messages from one sender, each recipient receives them in that sender’s send order.
  • Given server acceptance of a send whose recipient handler has not completed, the success response confirms routing acceptance without waiting for handler completion.
  • Given join, leave, and send requests, responses carry the matching requestId and result operation, with ok and either data or error according to outcome; successful send and leave responses contain data: null.
  • Given a malformed envelope, forbidden chat, missing authorized resource, unjoined send, absent owner, or internal failure, the error response contains the corresponding specified code and a human-readable message.
  • Given an unauthorized request for a missing chat resource, the response is forbidden rather than not_found.
  • Given malformed JSON or an invalid envelope, the server returns invalid_request with a usable requestId or null, keeps the connection open, and leaves Chat state unchanged.

Browser library

  • Given send, join, and leave operations, each returns a promise settled by its matching acknowledgment; join resolves with the owner-status booleans, while send and leave resolve without a value.
  • Given a failed request, its library promise rejects rather than resolving successfully.
  • Given handler registration, it synchronously returns an unsubscribe function that removes that registration without replacing or removing other registrations.
  • Given multiple handlers for one event name, all receive chat identity, sender, and body in that argument order, with independent deep copies per handler.
  • Given a handler mutating its inputs, subsequent handlers receive unaffected values.
  • Given multiple handlers including a pending asynchronous handler, invocation follows registration order without waiting for asynchronous completion.
  • Given a handler throwing or rejecting asynchronously, the failure is logged locally and other registered handlers still receive the event.
  • Given a received event with no registered handler, the library ignores it without failure.
  • Given multiplayer and another addon registering event handlers, both use the same registration and delivery mechanism.
  • Given a connection opening or closing, registered lifecycle listeners receive bus.connected or bus.disconnected respectively, with null chat, sender, and body arguments.
  • Given a server status notification for the current chat, bus.status listeners receive its chat identity, a null sender, and the owner-status booleans in the body.
  • Given an attempt to send a reserved lifecycle event through the application send operation, it is rejected rather than delivered as an application event.
  • Given a body that cannot be serialized as JSON, including a circular object or BigInt, the library rejects locally, transmits nothing, and leaves the connection open.
