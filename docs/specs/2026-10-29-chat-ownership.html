Chat Ownership

October 29, 2026

Problem

A scene owner needs to create a persistent SillyTavern Character Group Chat containing multiple Account cards representing participating server accounts and multiple Character cards representing scene characters, then add a chat to that group and reopen its transcript.

Selected guests need to discover the shared group in their normal character listing and open and read its chats, including while the owner is offline. This establishes a readable shared scene before participants begin playing together.

SillyTavern currently treats group members as local characters and serves groups, chats, and character portraits from the logged-in account’s storage. It does not provide the cross-account discovery and authorized reading needed for this experience.

Solution

This work implements the addon entirely in the frontend/browser. It makes no server-side or Plugin changes.

The creating account owns the group. Its stored group and transcripts are the authoritative source; guests access that source rather than independent copies.

The addon extends SillyTavern’s existing group creation and chat interface. Character membership retains its native representation. Account membership uses account identifiers, with each Account card displaying the account’s name and account avatar. Ownership and account membership are stored in the group’s JSON record alongside native character membership.

The addon presents shared groups in each participant’s normal character listing, identifies their owner, and displays their chats in SillyTavern’s familiar chat interface. It loads the group’s character cards and portraits with the transcript so guests can read the scene in context.

Behavior

Creating a group

The existing Create New Chat Group screen shows the creating account automatically as owner. Alongside Add Members, an Add Other Accounts section lets the creator select participating accounts. The creator does not select themselves.

Creation requires at least one Character card. Additional accounts are optional.

Account discoverability

Enabled accounts are eligible for selection by default, including when discreet login is enabled. Each account has an explicit opt-out setting, “Allow others to add me to shared groups,” enabled by default. Turning it off hides that account from future participant listings; existing memberships remain unchanged. Accounts already visible in an open selection list remain selectable and can be added.

Creating and reading chats

Adding a chat uses SillyTavern’s native New Chat behavior. Existing native transcript import behavior remains unchanged.

Guests can select and open a shared group’s chats and read their transcripts. For guest interactions beyond discovery, opening, and reading, broken behavior and unsecured changes—including changes to the owner’s group or transcripts—are acceptable in this milestone. Implementers must not hide controls, prevent writes, or add permission enforcement for those interactions.

Ownership indicators

A group owned by another account displays “Owned by <account name>” in its card. In grid view, a small badge overlays its circular portrait before the card is opened; the badge’s tooltip carries the same ownership label. The viewer’s own groups retain their normal icons.

Edge Cases

Shared chat fails to load
Show a load error and leave the stored chat untouched. Do not treat a failed load as an empty new chat.
Portrait is missing or fails to load
Use SillyTavern’s default avatar and continue displaying the group or transcript.

Dependencies

The Plugin specification must provide the following capabilities.

  • Account selection: supply authenticated users with eligible account identifiers, display names, and account avatars according to Account discoverability. Persist each account’s opt-out preference. Accept selections from an already displayed list even if an account subsequently opts out.
  • Group persistence: accept and retain ownership and account membership when creating and saving group records.
  • Shared-group discovery: supply the current account’s participating groups and their owner identities.
  • Shared-resource reads: supply group details, chat listings, transcripts, and the character cards and portraits needed to display the owner’s scene from another participating account. These reads must work without the owner’s browser being connected.

Testing Criteria

Tests run within the addon repository using fake Plugin responses and native-interface substitutes. They require neither a live Plugin nor a multi-account server. Other guest interactions require no functional tests; review verifies that the addon introduces no controls or guards prohibited by Creating and reading chats.

  • Given a logged-in account opening group creation, that account appears automatically as owner alongside character and other-account selection controls.
  • Given a creation form without Character cards, submission does not create a group.
  • Given a creation form with a Character card and no additional accounts, submission creates an owner-only group.
  • Given multiple selected Character and Account cards, the saved group retains the creator’s ownership and both sets of membership after reload.
  • Given eligible account records, Account cards display the supplied names and account avatars.
  • Given an account with no saved discoverability preference, “Allow others to add me to shared groups” is on by default.
  • Given an account disabling discoverability, the addon persists the preference without requesting removal of existing memberships.
  • Given an eligible-account response while discreet login is enabled, the addon displays the supplied accounts for selection.
  • Given an account opting out after its card was displayed, the existing selection remains available for submission without a new eligibility check.
  • Given an existing group, adding a chat invokes native New Chat behavior and makes the resulting chat selectable within that group.
  • Given shared groups returned for the current account, they appear in the normal character listing.
  • Given a group owned by another account, its card identifies the owner and its grid portrait carries the ownership badge and tooltip.
  • Given a group owned by the current account, its grid portrait has no guest ownership badge.
  • Given an owner or guest selecting a stored chat, the supplied transcript renders in order with its speaker identities and available portraits.
  • Given shared resources available while the owner’s browser is disconnected, a guest can list and open the group’s chats without contacting that browser.
  • Given a failed shared-chat read, the addon displays a load error and issues no request to initialize or overwrite that chat.
  • Given a missing or failed portrait, the default avatar appears and the group or transcript remains displayed.
