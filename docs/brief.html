SillyTavern Multiplayer

Working concept brief · October 29, 2026

Purpose

Multiple humans play distinct characters in a shared scene with an AI GM. The motivating use is a couple playing Duo Fate together, with support for a variable number of participants.

Three core pieces

  1. Communication bus. Moves messages between participants through the SillyTavern server. Integration code and extensions can send messages and attach event listeners that take actions when messages arrive.
  2. Shared human conversation. Builds on SillyTavern’s group-chat interface. Players exchange successive user turns independently of AI generation, preserving speaker identity and a common scene history.
  3. Chat ownership. One participant owns the scene. Their browser runs generation and authoritative extension workflows. The owner supplies the world, NPC cards, lorebooks, and AI settings, and explicitly starts an AI turn with a button. Ownership also provides shared read access to the scene’s loaded lorebooks: all participants read the same source, including character sheets stored there by RPG Companion.

Creating a shared chat

The owner uses SillyTavern’s existing “Create New Chat Group” flow. Alongside “Add Members” for character cards, an “Add Other Accounts” section lets the owner select accounts on the same server to participate in the shared chat.

Guest experience

The shared chat group appears in each participant’s normal character listing. Guests see an ownership indicator on its card identifying it as someone else’s shared group. Opening it uses the familiar chat interface; the card and conversation otherwise look like ordinary SillyTavern groups and chats. Guests can open and read the scene while the owner is offline.

Participation

Participants log in with accounts on the same SillyTavern server. Each player participates through one active SillyTavern persona representing their PC.

Guests can edit and delete their own messages. The owner can edit AI responses and their own messages. The owner can delete messages throughout the shared history.

The owner’s browser must be available for play to advance. During an owner browser refresh, guests remain connected with their transcript and drafts while action submission and generation pause. Play resumes after the owner restores the session. Guests can disconnect and rejoin independently.

Specifications emerging from the concept

Plugin

  • Communication bus: participant addressing, message delivery, and extension listeners.

Multiplayer addon

  • Shared conversation: synchronized history, player identities, and separation of human turns from AI generation.
  • Chat ownership: adding participant accounts through group creation, generation authority, session recovery, shared access to group cards and portraits, and making each guest’s active persona available to the owner for inclusion in the AI context.
  • Shared lorebook access: a separate specification for the resource-sharing responsibilities within chat ownership.
